COUNTING WORK · LOOP GROWTH

Count the steps before naming the growth.

A loop is a repeated instruction. By counting how many times its body runs, we can describe how an algorithm’s work grows as its input gets larger.

One loop: work grows in proportion to n.

Suppose the input contains n items and we inspect each item once. The loop body runs once per item, so it runs exactly n times.

COUNT∑i=1n1=1+1+⋯+1=n
READ IT ALOUD

Add one for each index from 1 through n; that makes n total steps.

We sum 1 because each visit to the loop body contributes one counted step. For n = 4, the count is 1 + 1 + 1 + 1 = 4.

Two loops: count every inner run

Now let an outer loop run n times, and for each outer iteration let an inner loop also run n times. Each of the n outer passes contains n inner steps:

COUNT∑i=1nn=n+n+⋯+n=n×n=n2
READ IT ALOUD

Add n, once for each of the n outer iterations. The total is n squared.

With n = 4, the inner body runs four times on each of four outer passes: 4 + 4 + 4 + 4 = 16 steps.

Exact count

For this simplified example, the inner instruction runs exactly n2 times. At n = 4, that is 16.

Growth description

Big O describes an upper bound on how work grows for large inputs. This example has O(n2) work.

Big O is not an exact step count. For example, 3n2+5n+2 is O(n2): for large n, the squared term determines the growth rate. The exact running time still depends on the instructions, the input, and the machine.

Cases and bounds are different questions

Best, worst, and average case say which inputs we are measuring. Big O gives an upper bound for the chosen case. An average case is an average over an assumed distribution of inputs—not simply the most common input.

A tight bound describes growth from both above and below. It is written with Θ (“theta”). You do not need that extra notation for the examples in this lesson. See the letters and notation guide for a reference.

When the input size is multiplied by 10, a one-loop count is multiplied by 10. A two-loop count like n2 is multiplied by 100.

If the nesting depth also grows with n

Two fixed loops give n2 work. Now imagine building a sequence of n choices: there are n options for the first position, n for the second, and so on for all n positions. For n = 2, choosing 0 or 1 in each position gives 00, 01, 10, 11: 22=4 sequences. The number of complete sequences in general is:

n×n×⋯×n=nn (n factors). At n = 4, that is 44=256 complete sequences. This is O(nn) work. Counting all the recursive function calls gives the same growth class. Since the base also grows with n, nn grows faster than standard exponential forms such as 2n. This is not the same as merely calculating nn once.

A formula for the count is not the same as doing the work. In the simple operation-count model used here, print(n * n) performs a fixed number of high-level operations; it does not execute n2 loop steps. (For very large integers, multiplication itself takes longer as the numbers grow.) The recursive function actually builds the count by considering every possible sequence. Comments marked PSEUDOCODE stand in for the useful task a practical program would perform; the counter makes repeated work countable. We use this to illustrate growth, not as a recommended way to solve a practical problem.

Compare four growth patterns

Each function is shown in full so you can inspect it without compiling or running anything. The pseudocode comments name the useful operation being counted. For the recursive example, choices_left is the number of positions still to fill; reaching zero means one complete sequence has been processed.

N-to-the-n · O(nn) 
def count_sequences(choices_left):
    if choices_left == 0:
        # PSEUDOCODE: process this complete sequence.
        return 1  # count one such operation

    total_steps = 0
    for choice in range(n):  # try every option at this position
        total_steps += count_sequences(choices_left - 1)
    return total_steps

n = 4
print(count_sequences(n))  # 4**4 = 256 counted operations
Square · O(n2) 
def count_square_work(n):
    total_steps = 0
    for i in range(n):              # n outer passes
        for j in range(n):          # n inner passes per outer pass
            # PSEUDOCODE: compare items i and j.
            total_steps += 1        # count one comparison
    return total_steps

n = 4
print(count_square_work(n))        # 16 counted steps
Linear · O(n) 
def count_linear_work(n):
    total_steps = 0
    for i in range(n):      # one pass for each of n items
        # PSEUDOCODE: inspect item i.
        total_steps += 1    # count one inspection
    return total_steps

n = 4
print(count_linear_work(n))  # 4 counted steps
Constant · O(1) 
def count_constant_work(n):
    # PSEUDOCODE: read one fixed configuration setting.
    total_steps = 1  # fixed work; does not depend on n
    return total_steps

n = 4
print(count_constant_work(n))  # still 1 step

Same result, different amount of work: Fibonacci

The Fibonacci numbers start F0=0,F1=1. Each later number adds the previous two: Fn=Fn−1+Fn−2.

Short recursive version · exponential work

def fib_recursive(n):
    if n <= 1:
        return n
    # Recomputes earlier Fibonacci numbers.
    return (
        fib_recursive(n - 1)
        + fib_recursive(n - 2)
    )

Each call branches into two more calls, and many values are recalculated. Its call count grows exponentially; a familiar upper bound is O(2n). For n = 40, it makes 331,160,281 function calls.

Longer iterative version · linear work

def fib_iterative(n):
    previous, current = 0, 1
    for _ in range(n):
        previous, current = (
            current,
            previous + current,
        )
    return previous

It keeps only the last two values and advances once per number: O(n) work with O(1) extra stored numbers. For n = 40, it uses 40 loop passes. Both versions return F40=102334155.

This comparison counts high-level additions and function calls. Python integers can grow to many digits, so each addition eventually costs more than one machine-level step; that detail does not change the contrast between exponential and linear growth here. The recursive code is shorter, but it does much more repeated work.
