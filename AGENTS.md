# Math Refresher project instructions

These instructions apply whenever an agent works in this repository.

## Mathematical content and notation

- Before adding or changing a mathematical term, symbol, or formula, check whether the learner-facing notation references also need an update. Define the role and range of every new letter or index in `docs/letters.html`; add reusable notation to `docs/quick-reference.html`; add unfamiliar terminology to `docs/glossary.html`; add links between the relevant entries and lessons. Do not assume that updating only the lesson is sufficient.
- If a formula introduces an indexed list or sum, explain what the index selects, the allowed range, and how to construct the entries or terms from concrete inputs. Define every symbol and state the assumptions.
- Do not use formulas as unexplained shortcuts. State the question being answered, show where the inputs come from, and explain why the formula follows. Distinguish counts, probabilities, estimates, and proofs. Start from a small concrete example, substitute values into the *whole* term, show the intermediate calculation, and only then generalize. State boundary cases and whether endpoints are included.
- For each key new formula, pair the MathML with a natural **NOTATION / READ IT ALOUD** explanation of the complete relationship (not merely the symbol names). Keep the spoken reading visually attached to its formula, with expansions at normal weight and numeric substitutions clearly distinguished. Teach readers to identify the main operation, bounds/conditions, symbol roles, and small substitutions before translating to code. Keep each lesson focused on one goal; mark untaught ideas as brief previews and link to their introduction. Synthesis pages may combine already introduced ideas.
- Clarify domains, units, and model assumptions. For probability, favorable/all outcomes requires finite equally likely outcomes; say when cases are disjoint or events independent rather than silently adding or multiplying probabilities. Separate a proof about a model from evidence that its assumptions describe reality; simulations and code checks are not general proofs.
- Write handbook content in English. Explain unfamiliar notation and terms plainly when first used, and use native MathML Core with an adjacent LaTeX comment as the editing aid for displayed or inline formulas.
- When using source material under `example/` or other references, read the complete relevant file and audit its useful examples—not just the one that prompted the change. Fact-check and resequence examples; correct ambiguities or errors and state scope limitations rather than silently omitting material. Treat existing references as selective sources, not content to port wholesale. If a specific external passage is needed, ask for its link/excerpt.
- Keep glossary entries concise: plain-English meaning, small example, lesson link. Define terms locally on first use even if the glossary already contains them. Keep `docs/quick-reference.html` a fast lookup aid, not another full lesson; references should remain accessible without losing the current page.

## Python and page structure

- Python is optional and supports visible reasoning; it does not replace an explanation or proof. Label comparisons, approximations, assumptions, and model limitations accurately. Start with explicit arithmetic, variables, and loops; introduce built-ins and library shortcuts afterward, explaining what they hide. Show only useful progressive variants, make each displayed variant loadable in the same shared editor and runnable with the same result, and explain the change between versions.
- Map code variables, model constants, units, and bounds to the math. Derive numeric bounds from named inputs; explain inclusive math bounds versus Python `range`'s excluded stop (and `randint`'s included endpoints). For exact rational results prefer `fractions.Fraction` when helpful; introduce `decimal.Decimal` for base-10/controlled precision only with an explanation of rounding and string construction.
- Keep site code in HTML, CSS, and plain JavaScript (not TypeScript). Pages must remain openable locally without a backend or build step; the optional Python editor uses Pyodide in a Web Worker and may require network access to fetch its runtime on first use. Do not suggest that a timeout is a perfect security sandbox.
- Keep the shared editor's output panel inside its own `section.code-section`. Put optional alternative code cards in a separate sibling section below the editor/output section, following the structure on `docs/products.html`; do not place code-variant cards inside `.output-panel` or `.code-section`.
- Keep the shared navigation and page conventions consistent. Maintain the grouped sidebar, non-destructive reference dialogs, current-page indication, and top/bottom previous/next links for the **core** sequence. Keep practice outside that sequence; do not link reader-facing placeholders. Update the glossary, quick reference, overview, and `PLAN.md` when the new material makes those references stale.
- Distinguish guided **worked examples** (full reasoning visible) from optional **practice** (paper-first challenge; hints and worked reasoning in separate, initially closed native `<details>`; Python separate and optional). Practice keeps the shared shell but uses its scoped workbook style. State rules and assumptions up front, use small printed datasets, ask at least one “why?” question, and do not invent regional game rules. Only call a strategy optimal when justified.
- For hypothetical health scenarios use explicitly invented rates, and keep incubation (infection to symptoms) separate from infectiousness. For ML/decision previews, distinguish hand-chosen toy weights from trained parameters; scores are not probabilities or guarantees, similarity depends on features and scaling, and predictions from historical data do not establish causation or guaranteed prices.

## Validation

- Build with `bash scripts/build_site.sh` and run `git diff --check` after edits. Put helper/build/check scripts in `scripts/`; run Python helper scripts with `uv run`, declaring third-party dependencies in inline PEP 723 metadata rather than adding project-wide one-off dependencies.
- Check local links and fragments after adding or moving anchors. Independently verify mathematical answers, edge cases, units, formula/LaTeX-comment agreement, and executable examples. Test relevant page rendering and interactive code-loading behavior when practical. For practice, check keyboard/touch `<details>`, hidden editor initialization, narrow tables, contrast, and sidebar consistency. Review math embedded in long prose (especially stacked fractions, limits, and several formulas in one paragraph) at desktop and narrow widths. Move dense calculations onto separate, readable formula lines rather than shrinking the text to make them fit.
- Keep durable decisions and learning-path changes in `PLAN.md` rather than relying on chat history. Treat its topic lists and proposed practice pages as a roadmap, **not** as a mandate to publish unfinished pages.
